# Phase 1: Active Directory Enumeration and Credential Access Attack Chain

## Phase 1 Overview

Phase 1 documents the first complete Active Directory attack-and-detect chain performed in the authorised lab environment.

The purpose of this phase was to simulate realistic attacker behavior against an Active Directory domain, collect the resulting telemetry, and validate Microsoft Sentinel detection logic across each stage of the activity.

This phase focused on:

- Reconnaissance
- Authentication testing
- Password policy enumeration
- Credentialed domain enumeration
- Password spraying detection
- Successful authentication correlation
- Post-authentication discovery
- SMB share enumeration
- Kerberoasting detection
- AS-REP roasting detection

The scenarios were executed from a controlled Kali-Red host against the lab domain controller and were monitored using Windows Security Events, Microsoft Sentinel, and KQL-based detection logic.

## Project Scope

This work was performed only in an authorised lab environment.

The environment was created for purple team learning, detection engineering, and defensive security validation. The objective was not only to simulate attack behavior, but to understand what telemetry is generated, how Microsoft Sentinel ingests the events, and how detections can be written or improved.

## Phase 1 Attack Chain

The Phase 1 attack chain followed this flow:

```text
Initial Reconnaissance
        ↓
Authentication Testing
        ↓
Password Policy Enumeration
        ↓
Credentialed Domain Enumeration
        ↓
Internal Password Spray
        ↓
Password Spray Followed by Successful Logon
        ↓
Post-Authentication Active Directory Enumeration
        ↓
SMB Share Enumeration and Access Validation
        ↓
Kerberoasting Detection
        ↓
AS-REP Roasting Detection
```

## Scenario 1: Initial Active Directory Reconnaissance

### Objective

The objective of Scenario 1 was to perform initial reconnaissance against the domain controller and identify exposed Active Directory-related services.

### Activity

Kali-Red was used to scan the domain controller and identify common AD services such as DNS, Kerberos, LDAP, SMB, and Global Catalog services.

### Detection Value

This scenario helped establish the start of the attack chain and created a baseline for understanding which domain services were exposed.

### Outcome

Scenario 1 was completed successfully and formed the reconnaissance stage of the attack chain.

## Scenario 2: Authentication Failure Testing

### Objective

The objective of Scenario 2 was to generate controlled failed authentication telemetry.

### Activity

A lab account was used to intentionally fail authentication in a controlled manner. This generated Windows Security Event ID `4625`.

### Detection Value

This scenario validated that failed logon events were being generated by the domain controller and collected into Microsoft Sentinel.

### Outcome

Scenario 2 was completed successfully.

---

## Scenario 3: Password Policy Enumeration

### Objective

The objective of Scenario 3 was to enumerate the domain password policy and understand the authentication controls in place.

### Activity

The password policy was queried from the lab environment to identify lockout thresholds, password length requirements, and related policy settings.

### Detection Value

Password policy enumeration is important because attackers often use this information to tune password spraying attempts and avoid account lockouts.

### Outcome

Scenario 3 was completed successfully.

---

## Scenario 4: Credentialed Domain Enumeration

### Objective

The objective of Scenario 4 was to use valid domain credentials to enumerate Active Directory information.

### Activity

A valid domain user account was used from Kali-Red to query domain information.

### Detection Value

This scenario demonstrated that valid credentials can be used for discovery activity after authentication.

### Outcome

Scenario 4 was completed successfully.

---

## Scenario 5: Internal Password Spray Detection

### Objective

The objective of Scenario 5 was to detect multiple failed authentication attempts against several domain accounts from the same internal source IP.

### Activity

Password spraying behavior was simulated from Kali-Red.

### Main Telemetry

| Event ID | Description |
|---|---|
| `4625` | An account failed to log on |

### Detection Logic Summary

The detection looked for multiple failed network logons from the same source IP targeting multiple unique accounts within a short time window.

### Outcome

Microsoft Sentinel generated an incident titled:

```text
LAB - Potential Internal Password Spray Against Active Directory
```

Scenario 5 was completed successfully.

---

## Scenario 6: Password Spray Followed by Successful Logon

### Objective

The objective of Scenario 6 was to detect when password spraying behavior is followed by a successful authentication from the same source IP.

### Activity

After failed authentication attempts were generated, a successful network logon was created from the same source IP.

### Main Telemetry

| Event ID | Description |
|---|---|
| `4625` | Failed logon |
| `4624` | Successful logon |

### Detection Logic Summary

The detection correlated failed logons against multiple accounts with a later successful logon from the same source IP.

### Outcome

Scenario 6 was completed successfully.

## Scenario 7: Post-Authentication Active Directory Enumeration

### Objective

The objective of Scenario 7 was to simulate post-authentication discovery using a valid domain account.

### Activity

The account used was:

```text
CORP\thabo.dlamini
```

The following domain enumeration activities were performed from Kali-Red:

```bash
net rpc user -U 'CORP\thabo.dlamini' -S 10.0.1.4
```

```bash
net rpc group members "Domain Admins" -U 'CORP\thabo.dlamini' -S 10.0.1.4
```

### Main Telemetry

| Event ID | Description |
|---|---|
| `4624` | Successful network logon |

### Evidence Summary

Sentinel confirmed:

```text
Event ID: 4624
Account: CORP\thabo.dlamini
Computer: DC01.corp.lab
Source IP: 10.0.2.4
Logon Type: 3
Authentication Package: NTLM
```

### Outcome

Scenario 7 was completed successfully.

## Scenario 8: SMB Share Enumeration and Access Validation

### Objective

The objective of Scenario 8 was to enumerate SMB shares and validate access using a standard domain user account.

### Activity

The account `CORP\thabo.dlamini` was used to access the `NETLOGON` share and test administrative shares.

Successful access:

```text
\\10.0.1.4\NETLOGON\
```

Denied access:

```text
C$
ADMIN$
```

### Main Telemetry

| Event ID | Description |
|---|---|
| `5140` | A network share object was accessed |
| `5145` | A network share object was checked to see whether the client can be granted desired access |
| `4624` | Successful network logon |

### Detection Value

This scenario demonstrated how network share access activity can be collected and reviewed after enabling File Share and Detailed File Share auditing.

### Outcome

Scenario 8 was completed successfully.

## Scenario 9: Kerberoasting Detection

### Objective

The objective of Scenario 9 was to simulate Kerberoasting behavior by requesting a Kerberos service ticket for an SPN-enabled account.

### Lab Configuration

The service account used was:

```text
svc_sql
```

The configured SPN was:

```text
MSSQLSvc/DC01.corp.lab:1433
```

### Activity

Kali-Red used Impacket to identify the SPN-enabled account and request a Kerberos service ticket.

```bash
impacket-GetUserSPNs corp.lab/thabo.dlamini:'REDACTED_PASSWORD' -dc-ip 10.0.1.4 -request
```

### Main Telemetry

| Event ID | Description |
|---|---|
| `4769` | A Kerberos service ticket was requested |

### Detection Value

This scenario confirmed that Kerberos service ticket request activity can be used to detect possible Kerberoasting behavior.

### Outcome

Scenario 9 was completed successfully.

---

## Scenario 10: AS-REP Roasting Detection

### Objective

The objective of Scenario 10 was to simulate AS-REP roasting against an account with Kerberos pre-authentication disabled.

### Lab Configuration

The account used was:

```text
svc_legacy
```

The account was configured with:

```text
Do not require Kerberos preauthentication = Enabled
```

### Activity

Kali-Red used Impacket to request AS-REP material for the configured account.

```bash
impacket-GetNPUsers corp.lab/ -usersfile users.txt -dc-ip 10.0.1.4 -no-pass
```

The output confirmed that `svc_legacy` returned AS-REP hash material. The comparison accounts `thabo.dlamini` and `svc_sql` did not have `UF_DONT_REQUIRE_PREAUTH` set.

### Main Telemetry

| Event ID | Description |
|---|---|
| `4768` | A Kerberos authentication ticket was requested |

### Detection Value

This scenario confirmed that Event ID `4768`, combined with `PreAuthType = 0`, can be used to detect possible AS-REP roasting activity.

### Outcome

Scenario 10 was completed successfully.

## Phase 1 Key Findings

### 1. Failed logon activity was visible in Sentinel

Microsoft Sentinel successfully ingested failed logon telemetry from the domain controller and supported password spraying detection logic.

### 2. Successful authentication could be correlated with earlier failed activity

Scenario 6 showed how failed attempts followed by a successful logon can increase alert severity and investigation priority.

### 3. Valid credentials enabled post-authentication discovery

Scenarios 7 and 8 showed how a normal domain account can be used to enumerate users, privileged group membership, and SMB shares.

### 4. File share auditing needed to be enabled

Scenario 8 showed that SMB activity may not be visible until File Share and Detailed File Share auditing are enabled.

### 5. Kerberos events may appear in different Sentinel tables

Scenario 9 showed that Event ID `4769` was visible in the `WindowsEvent` table, even when it was not immediately visible in `SecurityEvent`.

### 6. EventData parsing was required

Scenario 10 showed that important fields such as `PreAuthType`, `TicketEncryptionType`, source IP, and target username may need to be parsed from raw `EventData`.

## Phase 1 Conclusion

Phase 1 successfully demonstrated a complete Active Directory enumeration and credential access attack chain in an authorised lab environment.

The lab progressed from reconnaissance and authentication testing into password spraying, successful logon correlation, post-authentication discovery, SMB share access validation, Kerberoasting, and AS-REP roasting.

Microsoft Sentinel was used to validate detection visibility across the attack chain. The project also demonstrated important detection engineering lessons, including the need for correct audit policy configuration, correct DCR collection scope, table validation between `SecurityEvent` and `WindowsEvent`, and raw `EventData` parsing.

Phase 1 is complete.

The next stage is Phase 2, which will focus on detection engineering, incident triage, response actions, hardening recommendations, and retesting after remediation.
